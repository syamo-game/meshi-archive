# 認証と公開時の設定

## 秘密情報と実データ

秘密情報は環境変数または権限を制限した`.env`で管理します。実際のAPIキー・DB・投稿・店舗写真はコミットしません。公開前には対象ファイルそのものとGit履歴を確認してください。

## Webを外部公開する場合

本番用のCompose、接続先、プロキシ設定、デプロイ処理は同梱していません。実行環境に合わせて用意してください。

| 設定 | 条件 |
| --- | --- |
| `APP_ENV` | `production` |
| `SECRET_KEY` | 32文字以上のランダム値 |
| `DISCORD_CLIENT_ID` / `DISCORD_CLIENT_SECRET` | Discord OAuthの設定 |
| `DISCORD_REDIRECT_URI` | HTTPSのcallback URL |
| `ADMIN_USER_ID` / `WEB_ADMIN_USER_IDS` | 少なくとも1人のWeb管理者 |
| `HTTPS_ONLY` | `true` |
| `ALLOW_ANONYMOUS_READ` | `false`または未指定 |
| `FORWARDED_ALLOW_IPS` | リバースプロキシの実際の接続元IP |

OAuth・管理者設定の不足や本番のHTTP用設定では起動を拒否します。旧パスワードのPOSTログイン経路・環境変数・Cookieでは認証できません。プロキシは転送ヘッダーを検証し、Webへの直接接続を制限してください。`*`の代わりにプロキシのIPを明示します。

## Webの権限とセッション

Discordの管理者は`ADMIN_USER_ID`と`WEB_ADMIN_USER_IDS`で指定します。閲覧者は、これらの設定に加え、`DISCORD_ALLOWED_USER_IDS`またはDBの`discord_viewers`に登録された利用者です。`/admin/users`では閲覧・管理者の権限を選んで追加・編集できます。サーバ設定で固定したユーザーの権限は画面から変更できません。Webの権限変更はBotの権限を変えません。IDの登録は許可の指定であり、本人確認はDiscord OAuthで行います。OAuthが未設定の場合は、IDを登録してもDiscordでログインできません。画面から追加したユーザーのID・権限は編集アイコンと保存ボタンで変更し、利用許可は削除アイコンで取り消します。登録元・操作者は通常の一覧に並べず、監査に保持します。設定由来の許可はサーバ設定で変更します。

管理者はDiscordでログインし、DBの`admin_sessions`を使います。有効期限は発行から24時間で、DBにはトークンのハッシュと認証情報に結び付けたHMACを保存します。ログアウト・期限切れに加え、該当Discord管理者の権限低下・ID変更・利用許可削除でも、対応する管理者セッションは無効になります。権限変更時に対象の管理セッションをDBから失効させ、再昇格しても旧Cookieを再使用できなくします。

閲覧者は署名付きCookieで認証し、Cookieの`max_age`は24時間です。管理者と同じ発行時点からの絶対期限や、端末別の失効機能はありません。静的ファイル以外のリクエストでは、管理者セッションをDBで照合し、Discord閲覧許可を設定とDBの登録から再確認します。必要なDB照会に失敗した場合は該当する認証情報を破棄します。

許可の追加・ID変更・権限変更・削除は`discord_viewer_grant_events`に操作者のDiscord ID、変更前後の権限とともに記録します。権限・許可世代・セッション失効・監査は同じトランザクションで確定します。監査に失敗した変更は保存しません。旧パスワードによる過去の監査は当時の記録として残します。

実際のDiscord OAuthや本番環境での操作は、自動テストの結果とは分けて、運用時に確認・記録してください。

## CIと依存関係

`constraints.txt`で依存関係を固定し、全テストとpip-auditを実行します。OSパッケージやPython本体はpip-auditの対象外です。CIではPostgreSQLを使った移行・競合・トランザクションの検証と、GitleaksによるGit履歴の秘密情報検査を行います。

CIの権限は`contents: read`だけです。本番用のSecrets、SSH接続、コンテナの発行は使いません。外部PRに本番資格情報を渡さない構成を維持してください。秘密情報検査の除外は、既知の固定メッセージ・合成画像ハッシュ・架空Discord IDの特定のファイルと行内容に限定しています。

GitHubではPR・CI成功を必須とするmain保護、Secret scanning、push protection、Dependabot、外部PRの実行承認を確認してください。

## バックアップとDB移行

店舗DBと画像保存先を組にしてバックアップします。CSVには画像本体が含まれません。スキーマ変更前は書き込みを停止し、バックアップの復元一覧とハッシュを検証してから更新してください。

既存環境のrevisionを確認して`alembic upgrade head`を実行します。今回の認証スキーマの最新版は`20261006_02`です。監査記録や管理者権限がある場合はdowngradeを拒否します。記録を消して拒否を回避する代わりに、バックアップを保全して復旧手順を確認してください。

# 画面のUI

店の一覧・詳細・店舗編集、ログイン・管理者ログイン・管理トップ・データ確認は、すべてBootstrap 5.3.8を使う。全画面で`bootstrap.min.css`と`explorer.css`を読み込み、ログイン2画面と管理トップ・データ確認では`admin.css`を追加する。

## 部品と配置

- 初期表示と条件解除後は「地域順（東京から）」にする。東京都のリストと同じ区順（千代田区・中央区・港区…）で、同じ区内はエリア名・店名・IDの順に並べる。都内の市町村、都外、分類できないエリア、未設定はその後ろに置く。全店舗を並べてからページ分割し、店名順・評価順などの明示的な選択は保持する。
- 「地域順（東京から）」「店名順」「店名順（逆順）」「エリア名順」「エリア名順（逆順）」「評価が高い順」「評価が低い順」「追加が新しい順」の表記を使い、選択欄と適用中の条件で揃える。地域のまとまりとエリア名の文字順を区別し、読み仮名による並び替えではないため「五十音順」とは書かない。「追加が新しい順」はUTCの登録日時を基準にし、取込時刻は使わない。CSV出力・再登録でも元の登録日時を保持する。
- ボタンは`btn`、検索は`input-group`と`form-control`、選択欄は`form-select`を使う。
- 公開画面の検索条件は折り畳まず常時表示する。入力欄の後に「検索」を1つだけ置き、選択変更だけでは送信しない。画面幅に応じてCSS Gridで折り返し、スマートフォンでは長いエリア名・カテゴリ名に1行分の幅を使う。店舗編集にはBootstrapの`row`・`col`を使う。
- 店のカードは`card`、ページ切り替えは`pagination`・`page-link`、無効なリンクは`disabled`を使う。
- 一覧の訪問状況と評価は、管理者でも閲覧用の表示に揃える。訪問済みは右上のチェック、評価は小さい5つ星で示す。変更は詳細の「店舗情報を編集」から行い、一覧に訪問切り替え・星の操作ボタンや、そのための空行を置かない。
- 店舗詳細ダイアログの閉じるボタンは右上の「×」にまとめる。下部に同じボタンのためのフッターは置かない。
- 管理者向けの「店舗情報を編集」は、詳細の上部で訪問状況・評価の横に置く。写真より前に表示し、検索条件を保ったまま既存の編集欄へ進める。
- 投稿画像はカード上部いっぱいの16:9のカバーにし、画像には`card-img-top`、情報には`card-body`を使う。写真の下に店名・評価・地域・カテゴリ、最後にMapと保存元へのリンクを置く。
- 全カードに同じ16:9の画像枠を設け、画像なし・読み込み失敗時は無地にする。無地部分には読み上げ対象や空のリンクを作らない。同じ行のカードは同じ高さに揃え、リンクを下端に配置する。表示切替は設けない。
- ギャラリーの列数には上限を設けない。画面幅とカードの最小幅に応じて増減させる。最小幅は`explorer.css`の`--place-card-min-width`で変更できる。
- 青は検索・保存・再試行など、その場で処理を実行する主要操作に使う。編集画面への移動、戻る、条件解除、ナビゲーション、Map・保存元のリンクは中立色に揃える。候補採用や変更しない承認などの副次操作にも中立色を使う。削除・統合・除外・CSVによる全件置換は赤とし、実行前に確認する。評価済みの星には黄を使い、未評価は5つの空星で位置を揃える。訪問済みはカード右上のチェックで示し、文字ラベルは詳細画面と読み上げに残す。
- Map・保存元へのリンクは、一覧でも詳細でも枠なしの下線付きリンクにする。保存元はURLから確認できる行き先に応じて「Xの投稿」「食べログ」「PDF」などを表示し、分類できない場合はホスト名を表示する。PDFという拡張子だけで「メニュー」とは断定しない。地図ピン・リンクのSVGは16px・線幅1.75で揃え、文字の矢印は使わない。文字ラベルを残し、リンク間の余白と36pxの高さで押しやすさを確保する。
- 公開画面の管理画面・データ確認への入口はフッターに置く。管理系画面のヘッダーは「ホーム」「管理」の2項目にする。「データ確認」は管理の下位画面なので、ヘッダーに並べず「管理 / データ確認」のパンくずで階層を示す。管理配下では「管理」を選択状態にする。
- ログイン・管理画面でも、フォーム、ボタン、カード、通知には共通のBootstrap部品を使う。データ確認の一覧・編集・プレビューなど、管理用の配置は`admin.css`で調整する。
- データ確認で入力を変えた場合は「修正して確認を終える」を使う。「変更せず確認を終える」とAキー、別の候補での確定は、表示中の元の値と入力が一致する場合だけ使える。元の値に戻せば再び操作できる。候補の確定はその場で保存するため、ボタンにも保存することを明記する。
- データ確認の処理中は関連操作を無効にし、実行したボタンと読み上げ向け属性で状態を伝える。失敗時は入力を保ち、操作欄の近くにエラーと再試行を表示してフォーカスを移す。
- データ確認の作業内容は「店・支店を確認」「エリア・カテゴリを確認」の説明付きボタンで切り替える。ボタンを押すと取得し、成功したときだけ選択表示と編集欄を切り替える。失敗時は元の内容と入力を保ち、同じ条件で再試行する。
- 通常の絞り込みは確認状況と店名だけにし、「絞り込む」で適用する。確認状況は「未確認」「あとで確認」「確認済み」「お店ではないと判断」。最後の選択肢は店・支店の確認だけで使う。続きの読み込みと件数更新には適用済みの条件を使う。
- 確認件数は現在の作業内容・確認状況・検索語に一致する項目数で、ページ分割前に集計する。1投稿に2店あれば2件、同じ店の別投稿も各1件と数える。取得エラーのある確認項目数と処理に失敗した投稿数は、全体の処理状況として別に表示する。
- 作業欄は「確認する項目」「元の投稿」「保存する店舗情報」の順に置く。確認に回った理由は日本語で示し、内部コードと処理記録は詳細欄にまとめる。理由は過去の記録として扱い、現在の状態と混同しない。
- 独自のボタンやフォームの見た目を重ねて作る代わりに、Bootstrapの部品・ユーティリティ・CSS変数を使う。

`explorer.css`には全画面で共有する色・文字・操作部品と、検索条件、ギャラリー、投稿画像、評価、標準のdialogの配置を置く。管理用の`admin.css`も同じBootstrapのCSS変数を使う。旧`style.css`の代わりに、この共通CSSと画面ごとの配置を使う。

## 画像の取得と保存

承認済み投稿の`SourceAsset`にある画像は、ローカル画像URLへの初回アクセスで取得・保存する。元画像を中央基準で16:9に切り抜き、960×540のWebPとして保存し、次回から既存ファイルを再利用する。一覧と詳細には加工済みのローカル画像だけを表示し、元画像URLへ直接つながない。詳細の「写真を拡大」から同じ画像を新しいタブで開ける。

画像の配信時にも、ログイン条件と、同じ投稿候補の店舗・メタデータが両方承認済みであることを確認する。DBに登録された画像だけを配信し、未承認の画像は保存済みでも公開しない。取得失敗は理由をログへ残し、HTTP 502で返す。次回アクセスでは再取得を試みる。

保存先は`SHOP_IMAGE_CACHE_DIR`で指定する。未指定時は`.shop-image-cache/`、Dockerでは`shopimages`ボリュームを使う。ファイル名は元画像URLのSHA-256なので、店舗IDや`SourceAsset.id`が変わっても、同じ元画像URLの画像SourceAssetを登録すれば既存ファイルを再利用できる。

閲覧前にまとめて取得する場合は、対象の確認と保存を分ける。`--message-id`は複数回指定できる。

```powershell
python scripts/cache_shop_images.py --message-id 12345678901234567
python scripts/cache_shop_images.py --apply --message-id 12345678901234567
```

取得先はXとDiscordの画像ホスト、および店舗専用ギャラリーを確認した公式ホスト`www.oimachi-tracks.com`に限定する。後者はこのホスト名だけを許可し、似た名前のホストや別のサブドメインは許可しない。HTTPS、各リダイレクトの接続先、MIME、20MiBの上限、4,000万画素の上限を検証し、失敗した画像は表示しない。エラーには`asset_id`、`message_id`、URL、HTTP状態を残す。`scripts/cache_shop_images.py`では閲覧前にまとめて取得できる。

写真の採用時は、店舗・支店との対応に加えて画像の内容も目視で確認する。OG画像や投稿・ギャラリーの先頭画像という理由だけでは採用せず、料理・飲み物、店舗外観、店内、店舗を説明する看板・メニューを選ぶ。人物主体の自撮りや肖像、施設共通ロゴ、店舗との関係が確認できない街路写真は除き、別の適切な写真を探す。判断できない場合は採用を保留する。

店名から新しい写真を探す処理はまだない。追加する場合は店名だけで決めず、地域・住所・支店と照合する。Google Places APIの画像には[キャッシュ・保存の制限](https://developers.google.com/maps/documentation/places/web-service/policies)があるため、この保存処理へ流用しない。

CSVの再登録は店舗・投稿・SourceAssetを置き換える。現在のCSVには画像SourceAssetが含まれないため、投稿から取得した写真は再登録後、加工済みファイルが残っていても表示されない。元画像URLの画像SourceAssetを投稿に再登録すると、URLが一致するキャッシュを再利用できる。この画像登録は自動復元されない。店舗IDだけには結び付けない。編集画面からアップロードした写真は、以下の店舗別の参照で保持する。

### 編集画面からの写真アップロード

管理者は店舗編集でJPEG・PNG・WebPのファイルを選び、16:9プレビューで確認してから、店舗情報と一緒に「保存する」で確定する。写真を選び直さなければ現在の写真を保持する。編集リンクはedit=trueを付け、編集画面の上部は店名・支店名だけにする。写真は差し替え欄のプレビューにまとめ、上部には重複表示しない。通常の店舗詳細とダイアログでは写真を表示する。プレビューは既存のBootstrapのratioとobject-fit-coverを使い、PCは編集欄の半幅、スマートフォンは全幅に置く。写真枠を縮める変更は加えない。

サーバーでも実際の画像形式、20MiB、4,000万画素を検証し、向きを補正して960×540 WebPへ加工する。Shop.image_keyを画像内容のSHA-256とし、SHOP_IMAGE_CACHE_DIR/uploads/{image_key}.webpへ保存する。同じ投稿の別店舗やSourceAssetは変更しない。配信先は/media/shop-uploads/{image_key}.webpで、現在の店舗参照とログイン・公開条件を確認する。

保存失敗時は元の写真とDBの店舗情報を保つ。非同期保存では編集フォームを置き換えず、入力値と選択Fileを残し、同じ「保存する」で再試行する。認証が切れた場合も自動遷移せず、再ログインを案内する。401・403で現在のCSRFを応答ヘッダーから受け取り、認証情報だけを更新する。通信断では保存済みか判断できないため、「保存結果を確認できませんでした」と表示する。

CSVにはshop.image_keyを出力し、店舗IDや行順が変わっても写真の対応と登録日時を引き継ぐ。画像本体はCSVに入らないため、uploadsフォルダーもバックアップする。列のない旧CSVや空のキーには、写真を店名などから推測して割り当てない。統合先に写真がなければ引き継ぎ、異なる手動写真が両方にある場合は統合を止めて消失を防ぐ。参照のなくなったファイルは配信せず、CSV復元や別店舗での利用に備えて保存先には残す。

## 詳細表示

詳細はブラウザー標準のdialogで開く。Bootstrapの`modal`クラスからCSS変数を継承し、内側には`modal-content`・`modal-header`・`modal-body`を使う。閉じる操作は右上の×にまとめ、下部の重複ボタンは置かない。

開閉は既存の`main.js`が担当する。BootstrapのJavaScriptによる別の開閉処理を加える代わりに、この処理を維持する。検索条件、戻る操作、Escape、開く前のスクロール位置とフォーカス復帰を残すため。

## 配布ファイルの更新

CSSとMITライセンスは`web/static/vendor/bootstrap-5.3.8/`に同梱している。公開・ログイン・管理の各画面で同じ配布CSSを使い、表示時にはCDNへ接続しない。既存のGoogle Fontsの利用は変更していない。

[公式ドキュメント](https://getbootstrap.com/docs/5.3/getting-started/introduction/)にある配布CSSとSHA-384を確認して更新する。現行CSSの公式ハッシュは次の値。保存ファイルの末尾には改行が1つ付くので、検証テストではその改行だけを外して比較する。

```text
sRIl4kxILFvY47J16cr9ZwB07vP4J8+LH7qKQnuqkuIAvNWLzeN8tE5YBujZqJLB
```

更新時はテンプレートの配布パスとハッシュ検証テストを更新し、320pxから大型画面まで確認する。横のはみ出しだけでなく、長いカテゴリ名、詳細の背景と余白、星とリンクの操作領域も確認する。ログイン、管理者ログイン、管理トップ、データ確認でも、入力欄・ボタン・通知が読めることと、編集やプレビューの配置を確認する。

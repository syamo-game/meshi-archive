# システム構成

## 全体像

Meshi Archiveは、Discordの投稿を店舗情報へ変換し、根拠が十分な店舗だけを通常一覧へ公開します。

```text
Discord
  └─ Discord Bot
      ├─ 投稿、埋め込み、リンク、添付メタデータを保存
      ├─ 承認済みの同一出典なら店舗との対応を再利用
      ├─ OpenAI Responses APIで店舗への言及を抽出
      ├─ JSON-LDとWeb検索から候補を収集
      └─ 強い一致根拠がない言及をデータ確認へ送る

PostgreSQL
  ├─ FastAPI + Jinja2 Web
  ├─ Discord Bot
  └─ Alembic migration
```

本番はDocker Composeで`db`、`migrate`、`web`、`bot`を動かします。Webはリバースプロキシ経由で公開し、PostgreSQLは内部ネットワークだけに接続します。

## 店舗同定

1. Discord投稿を`messages`へ保存し、リンク、埋め込み、画像、添付を`source_assets`へ分けます。URLはサービス名、外部投稿ID、正規化URLへ分解し、内容のフィンガープリントも記録します。
2. URLまたは埋め込みだけを含む投稿で、SNSの出典IDが1件だけあり、その出典の過去の承認済み言及がすべて同じ店舗を指す場合は、その対応を再利用します。Discordが埋め込み用に生成したプレビュー画像は判定から除きますが、利用者が添付した画像やファイルがある投稿は再利用しません。この経路では抽出モデル、Web検索、画像解析を呼びません。
3. 再利用できない投稿は、投稿単位で店舗への言及を抽出します。店名、支店名、エリア、カテゴリは別の値として保持します。
4. 店名・支店名・エリアが、店舗本体または承認済み言及から作った別名のうち1店舗だけと完全一致すれば、外部検索を行わず、その店舗へ結びます。
5. 投稿内の店舗ページからJSON-LDを取得できる場合は、Web検索より先に候補化します。
6. 候補が不足する場合だけWeb検索を使います。Responses APIから検索元URLも受け取り、`canonical_url`と`evidence_url`を個別に照合します。引用されていないURLは捨て、外部IDは残った既知サービスURLからサーバー側で再抽出します。
7. 強い一致規則と画像規則で決まらない場合に限り、店名の一意な最高matching scoreが0.80以上の候補を1件選びます。その引用ページを安全なHTTP取得処理で読み、同じページの一意なJSON-LD、または同じ可視テキスト要素にある店名と完全な住所から店舗を確認できた場合だけ検証済みとします。見出しと別要素の住所は所属を証明できないため組み合わせません。
8. テキストと検証済み候補で決められず、有効な看板、メニュー、レシート画像がある場合だけ画像解析を使います。自動同定では候補店名を与えずに画像を読み、承認済み店舗かサーバーで取得した構造化データとの一致を確認します。
9. 新規作成候補の外部ID、電話と住所を既存店舗と再照合します。承認済みの1店舗へ矛盾なく一意に衝突する場合は新規作成せず、その店舗へ結びます。
10. 自動確定できない言及は、店舗レコードを先に作らずデータ確認へ送ります。

通常のリアルタイム処理と履歴同期では、通常抽出で店名を得られず、投稿内にリンクまたは埋め込みURLがある場合だけ出典探索を1回行います。固定した再処理対象の復旧でも、同じ経路を明示的に有効化できます。各店舗言及には元出典URLを1件割り当て、入力URLと検索の引用元が一致し、その出典の埋め込み情報または安全に取得したページ上で店名・支店名・管理語彙の地域を同時に確認します。複数店舗のうち一部だけ確認できない場合も言及を削除せず、元出典未確認としてデータ確認へ残します。見つかった店名はまだ候補として確定せず、別のWeb検索を1回行ってから既存の判定規則へ渡します。二段目でも候補URLが検索元に含まれることを確認します。元投稿のURLと、同じX・YouTube・既知店舗サービスURLの別表記や下層ページは、独立した根拠として数えません。この経路では画像解析も行いません。探索できる出典がない場合や、出典からも店名を確認できない場合は未特定としてデータ確認へ送ります。

抽出モデルと解決モデルは`EXTRACTION_MODEL`と`RESOLUTION_MODEL`で設定します。起動時に利用可否を確認し、利用不能でも別モデルへ自動切替しません。

エリアは47都道府県の市区町村（政令市の行政区、町・村を含む）を管理し、東京都は区市町村の下に駅・街を持ちます。市区町村まで分かれば登録でき、駅・街の指定は任意です。自治体コードを持つ公式マスターと東京の駅一覧を同梱し、実行時の外部API取得は行いません。出典、基準日、生成手順は `web/data/README.md` に記載しています。同名自治体は都道府県・郡・市とコードで区別し、政令市の区は市名を含めます。複数自治体にまたがる駅はそれぞれの対応を保持し、店の市区町村は住所で判定します。

既存の駅・街・交通拠点の通称は保持し、新しい自治体の保存値は都道府県を含む正式名称、東京の新駅は自治体と駅名を組み合わせます。粒度が曖昧な `東京` や、都道府県を特定できない同名自治体は自動分類しません。既存の非管理語彙は根拠なしに値・確認状態・公開状態を変えず、個別のデータ補正で扱います。抽出値を管理語彙へ直せない場合も原文は `shop_mentions` に残します。候補ページの完全住所から自治体と明記された駅・街を特定でき、原文の地域と矛盾しない場合は、その管理語彙を `shops.area` へ採用できます。検索候補のエリア欄だけでは補完しません。

自治体だけの地域は公開メタデータに使えますが、店名と自治体の一致だけでは既存店舗へ自動で結びません。画像から読んだ店名と自治体の一致、承認後の再評価でも同じ制限を適用し、確認済み住所・電話・外部IDなどの根拠を必要とします。編集画面は全国マスターを都道府県・地名で絞り込め、JavaScriptなしでも全候補を選択できます。検索画面は登録済み店舗がある地域だけを表示します。

## 自動確定

既存店舗へ結び付けるときは、次のいずれかを満たす場合だけ自動確定します。候補同士に支店、電話、住所の矛盾がある場合は確定しません。

- 正規化した店名・支店名・エリアが、承認済みの既存店舗1件だけと完全一致
- 同一サービスの外部IDが完全一致
- 電話番号が完全一致し、店名類似度が0.80以上で支店名に矛盾がない
- 住所が完全一致し、店名類似度が0.90以上で支店名に矛盾がない

画像を使う場合は、Discord画像が1枚だけで、画像内の店舗も投稿内の店舗言及も1件だけであることを条件に加えます。画像の店名・支店名と投稿由来のエリアが承認済み店舗1件だけに一致する場合も確定できます。画像が複数ある投稿や複数店舗を扱う投稿は、店名と電話・住所の対応を保証できないためデータ確認へ送ります。

新しい店舗を作るのは、取得したJSON-LDの店名と地域が言及に一致する候補が1件だけある場合、画像の電話・住所と一意に一致するJSON-LD候補がある場合、またはこれらで決まらずWeb候補の一意な最高店名一致スコアが0.80以上で引用ページの店名と住所を確認できた場合です。投稿に既知サービスの店舗URLがあるだけでは新規作成しません。店名一致スコアの規則では、投稿から取れた支店名が候補名にも含まれることを条件にします。投稿エリアを管理語彙へ正規化できる場合は候補との一致を必須とします。投稿エリアが欠けているか粒度が粗い場合は、候補の完全住所から管理語彙を一意に特定でき、投稿原文と矛盾しない場合だけ補完します。この経路では、住所が郵便番号と建物名を除いた町域部分まで採用エリアと一致する必要があります。

店名一致スコアは統計的な確率ではなく、候補を1件へ絞る順位付けです。0.80以上でもページ検証に失敗すれば自動登録しません。JSON-LDで確認できた値はその構造化データを保存します。可視ページで確認した場合は、店名、住所、引用済みURL、URLから再抽出した外部IDだけを採用し、ページ上で確認していない電話やカテゴリはWeb候補から引き継ぎません。

既存店舗への統合には店名一致スコアだけを使いません。一般のcanonical URLと根拠URL、候補の店名・支店名・エリア、電話、住所、既知サービスの外部IDを既存店舗と照合します。食べログなどのサービス名の別表記、IDの大文字・小文字、店舗トップとメニューなどの下層ページは同じ店舗IDへ正規化します。候補内で同じサービスのIDが食い違う場合や、複数のURL・外部IDが別々の既存店舗を指す場合は確定しません。支店名が片側だけにある場合も、同一サービスの外部IDが完全一致しない限り自動統合しません。出典探索では、独立検索の候補が0.80以上で、住所の町域まで一致することを先に確認します。その候補の正式名・支店・エリアが承認済み店舗1件だけと完全一致した場合に限り、既存店舗へ結びます。PostgreSQLではすべての新規店舗作成をトランザクション内で直列化し、並列処理による重複登録を防ぎます。画像だけを根拠に新しい店舗は作りません。

同じSNS投稿URLだけを、別々の店舗レコードを統合する根拠にはしません。同一出典の再利用は、過去の承認済み対応が1店舗に定まり、投稿に利用者の画像、添付、説明文がない場合に限ります。Discordが自動生成した埋め込みプレビュー画像は説明文や添付として扱いません。過去の対応が競合する場合は再利用しません。LLMの自己評価、候補順位、料理写真も単独では自動確定の根拠にしません。未知カテゴリは値を保存しますが、店舗の同定とは別のデータ確認へ送ります。

自動処理の根拠は`shop_mentions.resolution_basis`へ保存します。主な値は、同一出典の再利用、承認済み既存店舗との一致、検証済み候補、既存店舗との検証済み衝突、画像根拠です。同一出典の再利用では、元になった言及も`reused_from_mention_id`で追跡できます。

## データモデル

| テーブル | 役割 |
|---|---|
| `messages` | Discord投稿、処理状態、取得エラー |
| `source_assets` | 投稿内のリンク、埋め込み、画像、添付メタデータ、正規化した出典ID |
| `shops` | 確定した店舗情報、訪問状態、評価、メモ |
| `shop_mentions` | 投稿内の店舗言及、抽出値、解決状態、確認状態 |
| `resolution_candidates` | Webや構造化データから得た候補と一致根拠 |
| `sync_states` | チャンネルごとの連続処理済み位置 |
| `processing_runs` | モデル、トークン、検索、エラー、処理時間 |
| `review_events` | データ確認で行った判断の履歴 |
| `shop_redirects` | 統合前の店舗URLから統合先へ移すための対応表 |
| `import_batches` | CSV検証結果と明示適用の状態 |
| `import_rows` | 検証済みCSVの行データと取込バッチとの対応 |
| `lookup_cache` | URL取得結果と検索候補の期限付きキャッシュ |
| `login_attempts` | ログイン失敗回数、集計期間、試行を制限する期限 |
| `admin_sessions` | 管理者セッションのハッシュ、認証方法、有効期限 |
| `discord_viewers` | DBに登録したDiscord閲覧許可 |
| `discord_viewer_grant_events` | Discord閲覧許可を付与した操作者と日時の監査記録 |

Discord IDは17〜20桁の文字列として保存します。小数、科学表記、前後空白を許可しません。

## Web

FastAPIとJinja2で次の画面と認証経路を提供します。

- `/`：確認済み店舗の一覧、検索、絞り込み、並べ替え
- `/shop/{id}`：店舗詳細、訪問状態、評価、メモ
- `/admin/review`：投稿根拠と候補を比較するデータ確認
- `/admin`：CSVの検証と明示適用
- `/admin/users`：Discord利用ユーザーの一覧と閲覧許可の追加
- `/login`：閲覧用パスワードでのログインとDiscordログインへの導線
- `/admin/login`：管理者パスワードでのログイン
- `/auth/discord`、`/auth/discord/callback`：Discord認証の開始と結果の受け取り
- `/logout`：GETで確認画面を表示し、POSTで閲覧・管理者セッションからログアウト
- `/admin/logout`：POSTで管理者セッションからログアウト

管理操作には管理者認証とCSRF検証が必要です。データ確認の更新は言及と店舗のバージョンを照合し、二重送信や競合更新を拒否します。キューは、外部ID、店舗URL、電話と店名、住所と店名、または店名・支店名・エリアの一致に基づく「同じ店候補」を投稿単位でまとめて表示します。未検証のWeb候補は、候補名の類似度が0.80以上で支店の矛盾と候補内の強い識別情報の競合がない場合に限り、表示上のグループ分けへ使います。表示グループは一括統合や自動承認の根拠にはしません。

1件を承認すると、その承認済み店舗を基準に、未確認の言及だけを決定規則で再評価します。承認済み別名との完全一致または一意な検証済み候補があり、別店舗との矛盾がない言及だけを自動承認します。抽出エリアが空の場合は、店名と支店名が完全一致する検証済み候補のエリアだけを補助に使います。管理語彙外の非空エリア、未検証候補、保留中の言及、複数店舗へ分かれる言及、利用者入力が競合する店舗統合は自動変更しません。並行承認では候補行だけをID順にロックし、別処理がロック中の行は飛ばして次回の再評価へ残します。自動承認は`review_events`へ記録し、画面には解決件数を表示します。店舗の同定とメタデータの両方が確認済みの店舗だけを通常一覧へ表示します。

## 重複候補

重複検出は既定ではDBを変更しません。従来の店名・支店名・エリアによる候補レポートに加え、安全な統合計画を出力します。

安全な統合対象は、同一サービスの外部IDが完全一致するか、正規化した電話番号と完全な住所の両方が一致する承認済み店舗だけです。外部IDが一致せず支店名が片側だけにある組も対象外です。店名、支店名、エリア、カテゴリ、住所、電話、店舗URL、外部IDに矛盾がある場合や、訪問状態、訪問日、評価、メモが競合する場合は統合しません。明示的に適用した場合は、最小の店舗IDを残し、空欄だけを補完し、言及を移動し、旧URL用のリダイレクトと`review_events`を記録します。

## 同期と失敗状態

履歴同期は`sync_states`のチャンネル別カーソルから再開します。処理が成功または対象外になった投稿だけカーソルを進めます。

API、JSON、URL取得、画像取得の失敗は`processing_runs`へ記録します。処理に失敗した投稿は`failed`のまま残り、次回の同期で同じ投稿から再開します。

URL取得結果、候補検索、出典探索の生結果、店舗名・住所を確認したページ証明は30日間キャッシュします。出典との対応に失敗した結果は確定済みとしてキャッシュせず、生結果から再検証できます。並列数は既定2です。429と5xxは最大3回再試行し、各API試行を呼び出し回数へ数えます。再試行前に発生した費用を取得できない場合は、上限額を超えないよう予約額で多めに計上します。処理できなければ`failed`で停止します。設定や利用枠の問題は運用者が解消してから再実行します。
